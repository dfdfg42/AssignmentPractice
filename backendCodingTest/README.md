## 문제 1. 카드 조합 비교

두 플레이어가 각각 숫자 카드 5장을 들고 있다. 각 플레이어의 카드 조합 등급을 판정해 누가 이기는지 출력한다.

**입력**: 한 줄. 쉼표로 두 플레이어의 손패를 구분하고, 각 손패는 공백으로 구분된 정수 5개.

```
3 3 3 2 2, 1 2 3 4 5
```

**조합 등급** (높은 순):

1. 파이브 카드: 같은 숫자 5장
2. 스트레이트: 서로 다른 숫자 5개가 연속
3. 포 카드: 같은 숫자 4장
4. 풀 하우스: 같은 숫자 3장 + 같은 숫자 2장
5. 투 페어: 같은 숫자 2장이 두 쌍
6. 그 외

**출력**: 첫 번째 플레이어의 등급이 높으면 `First`, 두 번째가 높으면 `Second`, 등급이 같으면 `Draw`. 같은 등급끼리 숫자 크기는 비교하지 않는다.

**풀이 요약**: 카드 숫자별 빈도수를 내림차순으로 정렬하면 조합이 바로 드러난다. `[5]`는 파이브 카드, `[4,1]`은 포 카드, `[3,2]`는 풀 하우스, `[2,2,1]`은 투 페어. 스트레이트는 숫자 종류가 5개이고 최대-최소가 4일 때다. 등급은 `enum` 선언 순서로 비교한다.

## 문제 2. 고성능 크롤러

URL 목록을 받아 각 페이지의 본문을 파일로 저장하는 크롤러를 만든다.

**입력**: 표준 입력으로 URL이 한 줄에 하나씩 들어온다. 최대 1만 개.

**요구사항**:

- i번째 URL의 응답 본문을 `i.html` 파일로 저장한다 (1부터 시작).
- 요청이 실패하면(2xx가 아닌 응답, 타임아웃, 네트워크 오류) 파일 내용을 `FAILED`로 저장한다.
- URL 하나에 1초만 걸려도 순차 처리로는 1만 개에 3시간 가까이 걸린다. 전체가 현실적인 시간 안에 끝나야 한다.

**풀이 요약**: 고정 크기 스레드풀(`ExecutorService`, 50개)에 URL별 작업을 제출하고 `Future.get()`으로 전부 끝날 때까지 기다린다. 연결·요청 타임아웃은 10초. 어떤 예외가 나도 해당 파일에 `FAILED`를 쓰고 다른 작업에 영향을 주지 않는다.

## 문제 3. 채팅방 메시지 서버

여러 클라이언트가 방 단위로 메시지를 주고받는 HTTP 서버를 만든다.

**API**:

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/rooms/{roomId}/messages` | 본문 `{"sender": "...", "content": "..."}`. 저장된 메시지(id, sender, content, timestamp)를 돌려준다 |
| GET | `/rooms/{roomId}/messages?after={id}` | id가 `after`보다 큰 메시지만 돌려준다. `after=0`이면 방의 모든 메시지 |

**요구사항**:

- 메시지 id는 단조 증가해야 하며, 클라이언트는 마지막으로 읽은 id를 `after`로 넘겨 그 이후 메시지만 받아간다.
- 메시지는 24시간만 보관한다. 지난 메시지는 조회에서 빠지고 저장소에서도 정리돼야 한다.
- 여러 클라이언트가 동시에 보내고 읽어도 메시지가 유실되거나 순서가 꼬이면 안 된다.

**풀이 요약**: `ConcurrentHashMap<roomId, List<Message>>` + `AtomicLong` id 카운터. 쓰기는 `synchronized`로 직렬화하고, 읽기는 스트림으로 `id > after`와 24시간 이내 조건을 걸러 반환. `@Scheduled` 1분 주기로 만료 메시지를 삭제한다. `TestClient.main`으로 전송 → 전체 조회 → 추가 전송 → 이후분 조회 흐름을 확인할 수 있다.

## 문제 4. Key-Value 저장소

문자열 키-값을 저장하는 인메모리 저장소를 만든다. 세 가지 명령을 지원한다.

| 명령 | 동작 |
|---|---|
| `GET key` | 값을 돌려준다. 키가 없거나 만료됐으면 없음(null) |
| `SET key value` | 값을 저장한다. **키가 이미 있으면 값만 바꾸고 기존 만료 시각은 유지한다** |
| `EXPIRE key seconds` | `seconds` 초 뒤에 키가 삭제되도록 예약한다. 키가 없거나 이미 만료됐으면 실패 |

**요구사항**:

- 여러 클라이언트가 동시에 접근해도 안전해야 한다.
- 만료된 키는 실제로 메모리에서 제거돼야 한다 (조회 시점에만 걸러내는 것으로는 부족).
- 선택: 프로그램을 재시작해도 데이터가 남는 영속성, 네트워크로 접근하는 API.

**HTTP API** (선택 요건 구현):

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/kv/{key}` | `{"key","value"}`. 없거나 만료면 404 |
| POST | `/kv/{key}` | 본문 `{"value": "..."}` |
| POST | `/kv/{key}/expire` | 본문 `{"seconds": 60}`. 키 없으면 404 |

**풀이 요약**: `ConcurrentHashMap<String, Entry>`에 값과 만료 시각(`expireAt`, null이면 영구)을 함께 둔다. SET은 `compute()`로 원자적으로 값만 교체해 만료 시각을 보존한다. 만료는 두 겹으로 처리한다. GET 시점에 확인해 지우는 lazy 삭제와, 1초 주기 스케줄러가 전체를 훑는 eager 삭제. `KVStore.main`이 "SET 후 EXPIRE, 다시 SET 해도 만료 유지, 시간 지나면 null" 시나리오를 출력한다.
